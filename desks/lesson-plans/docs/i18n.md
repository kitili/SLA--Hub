# i18n substrate (next-intl)

The app is internationalized with [next-intl](https://next-intl.dev) v4 on the
Next.js 15 App Router. This document covers the **UI string catalogs** and
locale routing. For **translatable database content** (`*_en` / `*_sw` column
pairs), see the bilingual pattern in
[`schema-conventions.md`](./schema-conventions.md).

## Locales

| Code | Language | Role                |
|------|----------|---------------------|
| `en` | English  | Source / default    |
| `sw` | Swahili  | First translation   |

The set of locales and the default are defined once in
[`src/i18n/routing.ts`](../src/i18n/routing.ts) via `defineRouting`. Everything
else (middleware, navigation, request config, `generateStaticParams`) derives
from that single source.

### Adding a locale

1. Add the code to `locales` in `src/i18n/routing.ts`.
2. Create `messages/<code>/` with **every** catalog file and key present in
   `messages/en/` (the parity test enforces this).
3. Done — middleware, the `[locale]` segment, and the `LocaleSwitcher` pick it
   up automatically.

## Routing

- Locale-prefixed URLs: `/en/...` and `/sw/...`.
- [`src/middleware.ts`](../src/middleware.ts) runs `createMiddleware(routing)` and
  redirects locale-less requests (e.g. `/` → `/en`). Its matcher excludes
  `/api`, `/_next`, `/_vercel`, and any path with a file extension.
- The whole route tree lives under `src/app/[locale]/`. The root
  `src/app/layout.tsx` only forwards children; the real document shell
  (`<html lang>`, `<body>`, fonts, `NextIntlClientProvider`) is in
  `src/app/[locale]/layout.tsx`.
- Unknown locale segments are rejected with `notFound()` in the locale layout
  (the `[locale]` segment otherwise acts as a catch-all).

### Navigation

Import locale-aware navigation helpers from
[`src/i18n/navigation.ts`](../src/i18n/navigation.ts) instead of the Next.js
primitives:

```ts
import { Link, redirect, usePathname, useRouter } from "@/i18n/navigation";
```

`usePathname()` returns the pathname **without** the locale prefix, and `Link` /
`router.push|replace` add the active locale automatically. Pass `{ locale }` to
switch locales (see `LocaleSwitcher`).

## Message catalogs

UI strings live in per-area files under `messages/<locale>/*.json`. The file
list is defined once in [`src/i18n/catalogs.ts`](../src/i18n/catalogs.ts) and
merged per request by `src/i18n/request.ts`. Each file's **top-level keys are
the `t()` namespaces it owns**:

| File             | Namespaces it owns                        |
|------------------|-------------------------------------------|
| `common.json`    | `adminGate`, `common`, `nav`              |
| `member.json`    | `member`                                  |
| `admin.json`     | `admin`                                   |
| `errors.json`    | `errors`                                  |
| `lpteacher.json` | `lpHome`, `lpSearch`, `lpResults`, `lpPlan` |
| `lpfeedback.json`| `lpFeedback`                              |
| `lpadmin.json`   | `lpAdmin`                                 |
| `lpstudio.json`  | `lpStudio` (studio + batch generation)    |
| `lpmanage.json`  | `lpManage` (scheme/textbook/prompt admin) |

**Invariants** (pinned by
[`test/messages-parity.test.ts`](../test/messages-parity.test.ts)):

- Every key that exists in `messages/en/*` must also exist in `messages/sw/*`
  (and any future locale). English is the source of truth for which keys
  exist; other locales mirror its shape.
- Exactly **one** file owns each top-level namespace — the request-time merge
  is a shallow `Object.assign`, so a namespace defined in two files would
  silently shadow one of them.

### Reading strings

- **Server Components:** `const t = await getTranslations("nav");` then `t("dashboard")`.
- **Client Components:** `const t = useTranslations("common");` then `t("language")`.

`setRequestLocale(locale)` is called in the locale layout and in the home,
sign-in, and unauthorized pages — a next-intl requirement for any route that
should be statically renderable per locale. The remaining pages skip it: they
export `dynamic = "force-dynamic"` (they depend on the session cookie), so
per-locale static rendering does not apply to them. Add the call to any new
page that is meant to prerender per locale.

### Reference component

[`src/components/LocaleSwitcher.tsx`](../src/components/LocaleSwitcher.tsx) is the
reference for `useTranslations` + locale-aware navigation.

## File map

| File                              | Responsibility                                  |
|-----------------------------------|-------------------------------------------------|
| `src/i18n/routing.ts`             | `defineRouting` — locales + default (source)     |
| `src/i18n/navigation.ts`          | `createNavigation` — Link/redirect/router/pathname |
| `src/i18n/catalogs.ts`            | Catalog file list + file → namespace map         |
| `src/i18n/request.ts`             | `getRequestConfig` — per-request locale + messages |
| `src/middleware.ts`               | `createMiddleware` — locale negotiation          |
| `next.config.ts`                  | `createNextIntlPlugin('./src/i18n/request.ts')`  |
| `src/app/layout.tsx`              | Root passthrough layout                          |
| `src/app/[locale]/layout.tsx`     | Document shell + fonts + `NextIntlClientProvider` |
| `messages/<locale>/*.json`        | UI string catalogs (one file per app area)       |
| `test/messages-parity.test.ts`    | Pins file list, key parity, namespace ownership  |
